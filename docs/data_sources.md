# Data Source Architecture

This document explains the current data-source model for the Perfumery Dashboard. It is intentionally practical rather than perfect: the repo is buildable and useful, but source-of-truth boundaries are still split across several layers.

For the broader repo audit, see [repo_state_audit_2026-06-05.md](repo_state_audit_2026-06-05.md).

## Short Version

The app currently builds a live working model from these layers:

1. Embedded app data in `src/App.jsx`.
2. Structured registries in `src/data/*.json`.
3. Helper modules in `src/lib/*` that interpret, normalize, and reconcile the data.
4. Browser-local overlays in `localStorage`.
5. Supplier/evidence import and review payloads generated by UI flows or scripts.

Do not assume one file contains all truth. When data disagrees, prefer reviewed structured registries and helper logic over unreviewed imports, and prefer localStorage overlays only for that browser's local user state.

## Embedded Data In `src/App.jsx`

`src/App.jsx` currently contains most of the live app shell plus several large embedded data sets.

### `RAW_DB`

`RAW_DB` is the main embedded ingredient catalog. It contains live ingredient rows with identity, descriptive, chemistry, supplier, and compliance-adjacent fields.

Observed fields include:

- Identity/descriptive: `n`, `note`, `type`, `cas`, `inci`, `scentClass`, `scentSummary`, `scentDesc`, `descriptorTags`.
- Chemistry/physical: `MW`, `xLogP`, `TPSA`, `HBD`, `HBA`, `VP`, `densityGmL`, `densityGmL2`, `odorThreshold_ngL`, `vpConfidence`, `isIsomerMix`.
- Compliance and usage: `ifra`, `ifraLimit`, `ifraLimits`, `dilutionFactor`, `isUVCB`.
- Supplier/commerce: `supplier`, `char`, `rep`.

`RAW_DB` is live app data, but not the only authority. The app also enriches records through material normalization, IFRA package helpers, supplier registries, and local overlays.

### `PRICING`

`PRICING` is the embedded live supplier pricing/catalog structure used by procurement, basket, supplier, and formula cost workflows.

It includes supplier rows, product URLs, package sizes, units, prices, and stock/support flags. Some scripts intentionally patch the `PRICING` block after validating approved draft payloads.

### Seeded Formulas

Seeded formulas are embedded in `FORMULAS_INIT`. These are the base formula records used to initialize the formula library before user-saved local builds and formula state are layered in.

Saved builds and formula notes are not written back into `FORMULAS_INIT`; they live in browser storage unless a future explicit promotion flow is added.

The active seed library is now the focused 4-formula hero-scent development set:
`Random Concoction - Original`, `Skin-Air Bridge`, `Damp Shoreline v1`, and
`Damp Shoreline v2`. These records use explicit stable `formulaKey` values plus
`familyKey`, `variationRole`, `variationNumber`, `versionLabel`,
`revisionNote`, and `developmentStatus` metadata so the set can be treated as
one development family.

The previous 10-seed beach-line concept is legacy data. It is preserved in
[`docs/archive/legacy_formula_seeds_2026-06-07.md`](archive/legacy_formula_seeds_2026-06-07.md)
for reference and should not be reintroduced into the active UI unless a future
task explicitly creates a separate legacy/archive view.

Future formula seed resets should continue using explicit stable `formulaKey`
values. The retired legacy seeds relied on generated keys from formula name plus
array index, which made replacement and localStorage migration more fragile.

Retired legacy seed keys handled during active library construction:

- `seed-cabana-confessions-1`
- `seed-coastal-af-2`
- `seed-dominican-drift-3`
- `seed-heat-stroke-4`
- `seed-low-tide-lust-5`
- `seed-nauti-by-nature-6`
- `seed-rum-riptide-7`
- `seed-salty-skin-8`
- `seed-seasick-satisfied-9`
- `seed-wet-shore-10`

Saved-build guardrail: `buildFormulaLibrary` supports an optional
`retiredSeedKeys` key set and filters persisted records whose `formulaKey` is
retired and whose record is a seeded baseline or seeded override. The app passes
the retired legacy keys during active library construction so old seed-derived
overrides in `bb_saved_builds` do not reappear as active formulas after
`FORMULAS_INIT` has been replaced. Keep unrelated custom formulas and draft
versions intact, even if they were derived from a retired seed, unless the user
explicitly asks to remove them.

Active hero-scent seeds should use this shape:

```js
{
  formulaKey: "seed-hero-original",
  familyKey: "hero-scent",
  variationRole: "original",
  variationNumber: 0,
  name: "...",
  tagline: "...",
  desc: "...",
  versionLabel: "...",
  revisionNote: "...",
  developmentStatus: "active",
  ingredients: [
    { name: "Exact Catalog Material Name", g: 0, note: "top" },
  ],
}
```

## Structured Registries In `src/data/`

The `src/data/` JSON files are the most explicit structured data layer. They should be preferred over ad hoc edits when changing IFRA, evidence, normalization, or supplier registry support.

| File | Role |
| --- | --- |
| `src/data/ifra_combined_package.json` | Combined IFRA/runtime support package with metadata, identity map entries, compliance config, and stats. |
| `src/data/ifra_master_standards.json` | Extracted IFRA master standards data from source PDF processing. |
| `src/data/material_normalization.json` | Canonical material normalization, aliases, supplier links, helper seed support, and relationship data. |
| `src/data/source_document_registry.json` | Registered source documents and intake targets. |
| `src/data/evidence_candidate_registry.json` | Evidence candidates and candidate target state. |
| `src/data/supplier_product_registry.json` | Supplier products, supplier keys, product mappings, statuses, and registry notes. |
| `src/data/supplier_import_review_queue.json` | Review queue for supplier import items. |
| `src/data/supplier_price_draft_seeds.json` | Trusted review-only supplier price draft seeds. |

These files are not all equally safe to edit by hand. Prefer scripts, preflight validators, and focused tests when changing them.

## Helper Modules In `src/lib/`

The helper modules turn raw records and registries into app behavior.

| File | Role |
| --- | --- |
| `browser_storage.js` | Defines localStorage keys and defensive JSON/text read/write helpers. |
| `formula_runtime_helpers.js` | Formula keys, saved formula normalization, versioning, and comparison helpers. |
| `ifra_combined_package.js` | Main adapter for IFRA package data, material normalization, source/evidence/supplier registries, identity resolution, CAS comparison, and IFRA guidance helpers. |
| `perfumer_runtime_helpers.js` | Major business logic: formula math, procurement, bench stocks, founder planning, material truth, critiques, substitutions, and supplier adapter/review helpers. |
| `supplier_workbook_import_helpers.js` | Trusted workbook parsing, Fraterworks JSON/catalog import, compliance extraction, and reference workbook export helpers. |
| `*_preflight.mjs` | Validation helpers used before applying supplier/catalog draft payloads. |

For future code changes, helper modules are usually safer than editing `src/App.jsx`, provided the relevant tests are updated or added.

- `bb_local_draft_ingredients_v1`

LocalStorage data is real for the local user, but it is not committed repo truth. It can override or augment what the user sees in that browser, and it can contain sensitive material such as API keys.

## Supplier Import And Review Data

Supplier truth is split across several places:

- Embedded live pricing in `PRICING` inside `src/App.jsx`.
- Supplier registry records in `src/data/supplier_product_registry.json`.
- Review queue state in `src/data/supplier_import_review_queue.json`.
- Draft seed data in `src/data/supplier_price_draft_seeds.json`.
- Browser-local supplier data and review state in localStorage.
- Generated draft payloads from UI flows or scripts.
- Apply scripts under `scripts/` that validate and write approved data.

Supplier import flows should remain review-first. A Fraterworks or workbook import plan should not automatically become canonical ingredient truth. Imported supplier facts can support supplier records, local draft materials, review candidates, or approved payloads depending on confidence and operator action.

## Evidence And Source Document Registries

Evidence/source-document truth is centered on:

- `src/data/source_document_registry.json`
- `src/data/evidence_candidate_registry.json`
- Local files under `downloads/source_documents/` when present
- Inspection/generation/promotion scripts under `scripts/`

The evidence pipeline is meant to separate source acquisition, evidence candidate generation, review, and promotion. Source documents and candidates are not the same as canonical app truth until an approved promotion or apply step writes reviewed data into the appropriate structured layer.

## Script-Generated Review And Apply Payloads

Scripts and UI tools can generate JSON payloads for review. Common apply scripts include:

- `scripts/apply_supplier_import_drafts.mjs`
- `scripts/apply_catalog_row_drafts.mjs`
- `scripts/apply_catalog_supplier_links.mjs`
- `scripts/apply_catalog_supplier_prices.mjs`
- `scripts/promote_evidence_candidates.mjs`

Run these with `--dry-run` first. Inspect the output and `git diff` before applying for real.

Some scripts are read-only or report-oriented unless optional flags are used:

- `scripts/report_source_document_acquisition_gaps.py`
- `scripts/inspect_source_document_pdfs.py`
- `scripts/discover_supplier_documents.cjs` with `--dry-run`

Be careful with `--update-registry` and `--download` on discovery scripts because those can write registry entries or local files.

## Source-Of-Truth Decision Model

Use this decision model unless the specific code path proves otherwise:

1. **Base live app data** starts in embedded `RAW_DB`, `PRICING`, and `FORMULAS_INIT`. The current `FORMULAS_INIT` records are the focused 4-formula hero-scent development set; the prior 10-formula beach-line seeds are archived legacy references only.
2. **Canonical enrichment and compliance support** come from `src/data/` registries interpreted by `src/lib/ifra_combined_package.js` and runtime helpers.
3. **Supplier imports** are support/review data until approved and applied into supplier registries, normalization data, or embedded live pricing/catalog sections.
4. **Evidence candidates** are review artifacts until approved and promoted.
5. **LocalStorage edits** affect the current browser/user experience but do not become repo truth automatically.
6. **Generated payloads** are not truth until reviewed, dry-run, applied, and validated.

This hierarchy is not perfectly enforced everywhere in the UI. If a future task depends on precedence, inspect the exact component/helper path before changing behavior.

## Answers To Common Questions

### Where does ingredient truth live?

Ingredient truth is split:

- Live catalog presence and many display fields live in `RAW_DB` inside `src/App.jsx`.
- Canonical identity, aliases, supplier links, helper-source support, and normalization live in `src/data/material_normalization.json`.
- IFRA/identity support lives in the IFRA package data and `src/lib/ifra_combined_package.js`.
- Manual/local edits and draft ingredients can live in localStorage.
- Evidence candidates do not become ingredient truth until reviewed and promoted.

### Where does supplier truth live?

Supplier truth is split:

- Live supplier pricing used by the app lives in `PRICING` inside `src/App.jsx`.
- Supplier product registry truth lives in `src/data/supplier_product_registry.json`.
- Supplier import review state lives in `src/data/supplier_import_review_queue.json` and localStorage.
- Supplier price draft seeds live in `src/data/supplier_price_draft_seeds.json`.
- Browser-local supplier overrides/imports can live in `bb_supplier_data_v4`.

### Where does IFRA/compliance truth live?

IFRA/compliance truth should come from structured files and helpers:

- `src/data/ifra_master_standards.json`
- `src/data/ifra_combined_package.json`
- `src/lib/ifra_combined_package.js`

Embedded `RAW_DB` IFRA fields may still exist for display or legacy support, but future IFRA/compliance changes should use structured lookup files and helper logic. Do not add hardcoded IFRA limits casually.

### Where do user edits live?

Most user edits live in browser `localStorage`:

- Formula notes
- Saved builds
- Inventory
- Founder scenarios
- Manual record edits
- Local draft ingredients
- Supplier review state
- Evidence review state
- Bench stocks
- API key text

These edits are local to the browser profile unless exported or explicitly promoted through a repo workflow.

### What happens when data disagrees?

The current answer depends on the code path.

General guidance:

- UI display may prefer local manual edits or browser overlays.
- Compliance/IFRA decisions should prefer structured IFRA helpers and registries.
- Supplier imports with conflicts should remain in review rather than overwriting canonical data.
- Evidence candidates should remain candidates until promoted.
- Embedded live data remains the base app layer unless a reviewed apply script changes it.

If this is material to a change, inspect the relevant helper and add or update tests before changing precedence.

## Files To Avoid Editing Casually

- `src/App.jsx`: very large, high blast radius, contains live embedded data and UI.
- `src/data/ifra_master_standards.json`: generated/extracted structured IFRA data.
- `src/data/ifra_combined_package.json`: structured IFRA/runtime package.
- `src/data/material_normalization.json`: canonical material normalization and links.
- `src/data/source_document_registry.json`: source document registry.
- `src/data/evidence_candidate_registry.json`: evidence candidate registry.
- `src/data/supplier_product_registry.json`: supplier product registry.
- `package.json`, `package-lock.json`, and `vite.config.js`: dependency/build behavior.
- `public/index.html`, `src/App.jsx.backup`, and `beach-box-perfumery/*`: known stale/legacy areas that should be handled only in a dedicated cleanup task.

## Safer Places To Modify With Tests

- `docs/` for documentation changes.
- Focused helpers in `src/lib/` when covered by `tests/*.test.mjs`.
- `tests/` for helper behavior documentation and regression coverage.
- Preflight helpers in `src/lib/*_preflight.mjs`.
- Scripts under `scripts/`, especially when they support `--dry-run` and have clearly reviewed payloads.

Even in safer areas, run the relevant tests and `npm run build` before finishing.

## Uncertainties

- The exact precedence between localStorage overlays, embedded records, and registry data is not documented uniformly in code.
- The intended long-term storage model is unclear: local-only app, internal single-user dashboard, or shared product.
- The intended migration path from embedded app data to generated modules or JSON files is not yet defined.
- Some tracked legacy/stale files may still have historical value, but their current role is unclear.
